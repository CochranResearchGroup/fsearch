# Frozen native trigram prototype comparison plan

Frozen before implementation/measurement, 2026-10-04. Decision: ADR 0003. Source anchor: 5ec26bab. Isolated synthetic records only; no production changes or installation.

Compare the actual sequential headless matcher, native ASCII byte-trigram candidates, and SQLite FTS5 trigram candidates. Both accelerators retain the actual FSearch literal matcher and response builder. Unsupported Unicode queries and path mode scan; non-ASCII names remain a conservative candidate bucket. Preserve files-before-folders/name order, filters, literal punctuation, response limits, cached identity and truthful completeness. Candidate counts may differ; complete ordered results and response semantics must agree with the sequential oracle at 100,000 entries. Test one million only under the existing 64 MiB snapshot and 256 MiB worker address-space limits. A larger exhaustive oracle is test-only; do not increase public query caps.

Construct deterministic virtual filenames using the existing entry/snapshot format without materializing or scanning their roots. Include nested parents, mixed extensions, duplicates, literal punctuation, Unicode/case/normalization, raw non-UTF-8 names, long names, selective hits, absent trigrams and zero-hit queries with present trigrams. Run at least 100 warmed samples per designated query after explicit warmup; report nearest-rank p50/p95/p99. Each engine runs separately. Report snapshot size, load and index-build times, peak RSS/address space, posting/verification work and CPU. Native and SQLite candidate work must have finite explicit budgets; a bounded rejection is not a completed empty result.

Correctness gate: exact ordered results, status/completeness/truncation, root coverage and identity parity on all completed sequential-oracle cases; cap-rejected cases reported separately. Candidate intersection false positives must be rejected by the actual matcher. No indexed-root file syscalls in traced query runs; tracing measured separately from latency. Preserve failure receipts.

Exploration targets: selective matcher p95 under 5 ms at 100,000 entries, under 10 ms at one million if admitted; these are matcher/pipe prototype targets, not installed socket/MCP acceptance. Common, one/two-character, Unicode/path fallback and zero-hit cases reported individually. No aggregate average can hide fallback cost. Loading plus accelerator construction must be checked against the existing two-second startup bound; exceedance blocks production readiness even if warm queries are fast.

Stop after a reproducible native prototype, SQLite comparison, correctness/resource/isolation receipts and recommendation. No safe-refresh, monitoring, snapshot replacement or MCP implementation. No silently relaxed memory, startup or work caps. The compact posting representation is experimental and not a production format decision.

## Amendment before corrected comparison

The original matcher leaks the previous UTF builder string on every normalization; a repeated Unicode workload hits the unchanged 256 MiB AS cap. Preserve the failed run and reproduce it directly. The corrected comparison links a prototype-only copy of fsearch_utf.c freeing that owned string before replacement; the same repair applies to all three engines, with no production edit. Timings are therefore for the lifetime-repaired matcher. Ignore only wall-clock age_seconds and examined counts in parity; retain coverage timestamps and identity. An exhaustive test-only oracle may examine at most 1,000,100 records once per case, separately from publicly bounded benchmark requests. Broad posting lists use a sound sequential fallback (threshold 4096) rather than eagerly materializing/intersecting all candidates. Existing latency/resource targets remain unchanged.
